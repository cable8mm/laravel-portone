# PRODUCT_SPEC

## Purpose

- Product: cable8mm/laravel-portone (the "Package").
- The Package provides server-side PortOne V2 single-payment handling for Laravel applications through a Cashier-style interface.
- The Package publishes editable checkout starting-point files (a view, a script, a controller, and a route file) that the Developer copies into the Application.
- Term "Application": a Laravel application that installs the Package.
- Term "Billable model": an Eloquent model of the Application that uses the Billable trait defined in SCR-001.
- Root namespace of the Package: Cable8mm\LaravelPortone.

## Problem

- Laravel Cashier is not supported in Korea.
- Existing Laravel packages for PortOne are unmaintained.
- Applications have no maintained Cashier-style package for PortOne V2 payments.

## Product Goals

- Enable the Developer to attach payment capability to any Billable model.
- Enable the Developer to create a payment record before the Payer pays.
- Enable the Developer to obtain the values needed to start a PortOne browser payment.
- Enable the Developer to verify and complete a payment after the Payer pays.
- Enable the Developer to refund a payment fully or partially.
- Enable the Developer to list the payments of a Billable model.
- Enable the Developer to receive PortOne webhooks as Laravel events.
- Enable the Developer to publish editable checkout starting-point files into the Application.
- Enable the Payer to pay for an order in an Application and have the payment recorded as paid.

## Users

- Term "Developer": a person who installs the Package in an Application and calls its methods.
- Term "Payer": an end customer of the Application who pays through the PortOne browser SDK and the PG payment window.
- The Payer observes the Package only through the Application.
- The Payer starts a payment by clicking EL-026 when the Developer has included the files of SCR-006 in the Application.

## Inputs

- Term "Payment ID": a string generated by the Package that identifies one payment and is used as the PortOne payment identifier.
- Term "Customer ID": a string generated by the Package that identifies one Billable model.
- Developer method calls: defined by EL-001 through EL-008, EL-010, EL-042, EL-045.
- Test-support calls and commands: defined by EL-049 through EL-051.
- Configuration values: defined by EL-015 through EL-018, EL-022, EL-023, EL-033, EL-034.
- Developer-scheduled command and pruning, and the queued job they start: defined by EL-031, EL-032, EL-035.
- Payer action on the published view: defined by EL-026.
- HTTP requests to the routes of EL-030: defined by FR-042 through FR-056, FR-066, FR-067.
- HTTP POST request to the webhook route: defined by EL-011 through EL-013.
- PortOne API responses: defined in External Systems.

## Outputs

- Term "Customer record": a persisted record with the fields billable reference and customer_id.
- Term "Payment record": a persisted record with the fields below.
- Payment record field payment_id: string, unique across all Payment records.
- Payment record field billable: reference to the owning Billable model.
- Payment record field customer_id: string.
- Payment record field order_name: string.
- Payment record field amount: integer.
- Payment record field status: exactly one of PENDING, PAID, PARTIALLY_CANCELLED, CANCELLED, EXPIRED, AMOUNT_MISMATCH_CANCELLED, AMOUNT_MISMATCH.
- Payment record field cancelled_amount: integer, initial value 0.
- Payment record field paid_amount: integer or null, initial value null. The total paid amount PortOne reported when the Package confirmed the payment: set together with PAID (FR-023, FR-060) and with the amount-mismatch statuses (FR-069, FR-070). Null means PortOne has not reported a paid amount for the record.
- Payment record field paid_at: timestamp or null, initial value null.
- Payment record fields created_at and updated_at: timestamps.
- Method return values: defined per element in SCR-001 and SCR-002.
- Events: WebhookReceived, defined by EL-021; PaymentPaid, PaymentCancelled, PaymentPartiallyCancelled, PaymentFailed, defined by EL-038 through EL-041; PaymentExpired, PaymentPaidOnExpiry, PaymentAmountMismatchedOnExpiry, defined by EL-046 through EL-048.
- Console output: the PortOne payment response printed by EL-044.
- Published files: defined by EL-025, EL-028, EL-029, EL-030, EL-036.
- Webhook HTTP responses: defined by EL-014.
- Exceptions and error responses: defined by ERR-001 through ERR-019.
- Deleted Payment records: only those selected by EL-035.

## Constraints

- PHP version: 8.2 or later.
- Laravel version: 12 or later.
- The script of EL-028 requires the npm package @portone/browser-sdk to be installed in the Application.
- The controller of EL-029 requires the authenticated user model of the Application to use the Billable trait.
- EL-031 and EL-035 run only when the Application schedules them; EL-032 runs only when the Application runs a queue worker.

## External Systems

### PortOne V2 payment lookup

- The Package relies on PortOne returning, for a payment ID, the payment status.
- The Package relies on PortOne returning the total paid amount when the payment status is paid.
- The Package relies on PortOne returning the cancelled amount (amount.cancelled) of a payment. Verified by T-010 (tests/E2E/portone-payment-cancellation-observation.json): after a partial cancellation of 30 out of 100 the status is PARTIAL_CANCELLED with cancelled amount 30; after the remaining 70 the status is CANCELLED with cancelled amount 100. A paid payment reports cancelled amount 0 (tests/E2E/portone-payment-command-observation.json).
- PortOne names the partially cancelled payment status PARTIAL_CANCELLED; the Package's own status for it is PARTIALLY_CANCELLED.

### PortOne V2 lookup of abandoned payments

- Verified by T-021 (tools/probes/portone-abandoned-payment-observation.json) and T-003:
  - A payment whose window never opened: PortOne reports the payment unknown (PAYMENT_NOT_FOUND).
  - A payment whose window is open and not yet paid: status READY.
  - A payment whose window the Payer closed: status FAILED.
  - A payment ID whose lookup reported FAILED can still be paid later with the same payment ID; its status then becomes PAID.
- No lookup result means a payment can never be paid. The results that mean "not paid at the time of the check" for FR-061 are, by owner decision: PAYMENT_NOT_FOUND, READY, FAILED.
- Not observed: whether PortOne moves a long-abandoned READY payment to another status by itself. FR-061 does not depend on it.

### PortOne V2 payment cancellation

- The Package relies on PortOne accepting a cancellation request containing a payment ID and a reason.
- The Package relies on PortOne cancelling the full remaining amount when the request omits the amount.
- The Package relies on PortOne cancelling the given amount when the request includes an amount.
- The automatic cancellation of FR-068 is the same request as a full refund: PortOne does not know the amount the Package prepared, so a payment paid with a different amount is an ordinary paid payment to PortOne. Verified by T-025 (tests/E2E/portone-amount-mismatch-observation.json): after the automatic cancellation through EL-005 and through EL-032, PortOne reports the payment CANCELLED.

### PortOne V2 webhook delivery

- The Package relies on PortOne sending HTTP POST requests with the headers webhook-id, webhook-signature, webhook-timestamp.
- The Package relies on PortOne signing each request with the webhook secret.
- Transaction webhook types and their data (paymentId, transactionId, storeId, and cancellationId for cancellations) follow the PortOne webhook documentation as modelled by cable8mm/portone-php. Transaction.Paid and Transaction.Cancelled were observed live (tests/E2E/portone-webhook-observation.json). Transaction.PartialCancelled (after a partial refund) and Transaction.Failed (after the Payer closed the payment window) were observed live by T-028 (tests/E2E/portone-webhook-events-observation.json).

### PortOne V2 payment lookup response

- The keys listed in FR-079 follow the PortOne payment response documentation (customer, method, cashReceipt) and the live response recorded by T-030 (tests/E2E/portone-payment-command-observation.json): pgResponse is the PG's raw response as a JSON string and contains the card number and approval number; origin holds the Payer's ipAddress and userAgent; webhooks holds the webhook delivery history with URLs and signature headers.

### PortOne browser SDK

- The Package relies on the SDK function requestPayment opening the PG payment window for the values passed to it.
- The Package relies on requestPayment returning a result that carries an error code when the payment did not complete.
- The Package relies on requestPayment returning a result without an error code when the payment completed.

### PG channel

- The first payment channel used to verify the Package is NHN KCP.

## Functional Requirements

### Registration and configuration

- FR-001: The Package MUST be usable after installation without manual service provider registration.
- FR-002: The Package MUST publish its configuration file when vendor:publish runs with EL-019.
- FR-003: The Package MUST publish its migrations when vendor:publish runs with EL-020.
- FR-003a: When vendor:publish runs with EL-020, the Package MUST NOT publish a migration whose name without the date prefix already exists in the migrations directory of the Application, so that an Application that published an earlier version receives only the new migrations.
- FR-004: The Package MUST read configuration values from the Laravel configuration key portone.
- FR-005: When EL-017 is unset, the Package MUST send PortOne API requests to the PortOne default API base URL.
- FR-006: When EL-017 is set, the Package MUST send PortOne API requests to the value of EL-017.

### Customer

- FR-007: The Billable trait MUST add EL-001 through EL-008 to any Eloquent model that uses it.
- FR-008: EL-001 MUST return true if and only if a Customer record exists for the Billable model.
- FR-009: EL-002 MUST return the Customer ID of the Billable model, or null if no Customer record exists.
- FR-010: EL-003 MUST create a Customer record with a new Customer ID and return that Customer ID when no Customer record exists for the Billable model.
- FR-011: EL-003 MUST return the existing Customer ID and MUST NOT create a Customer record when a Customer record exists for the Billable model.
- FR-012: Customer records MUST persist across sessions.

### Payment preparation

- FR-013: EL-004 MUST create a Payment record with status PENDING, the given amount, the given order name, cancelled_amount 0, paid_at null, a new Payment ID, and the Customer ID of the Billable model.
- FR-014: EL-004 MUST create a Customer record for the Billable model by the rule of FR-010 when none exists.
- FR-015: Every Payment ID MUST differ from all other Payment IDs.
- FR-016: EL-004 MUST return the created Payment record.
- FR-017: EL-004 MUST NOT send any request to PortOne.
- FR-018: Payment records MUST persist across sessions.
- FR-019: EL-010 MUST return an array with exactly the keys paymentId, orderName, totalAmount, customerId, holding the payment_id, order_name, amount, and customer_id of the Payment record.

### Payment completion

- FR-020: EL-005 MUST look up the Payment record by the given Payment ID only among the Payment records belonging to the Billable model.
- FR-021: EL-005 MUST request the payment from PortOne by Payment ID when the Payment record status is PENDING or EXPIRED.
- FR-022: EL-005 MUST return the Payment record unchanged and MUST NOT send any request to PortOne when the Payment record status is PAID, PARTIALLY_CANCELLED, or CANCELLED.
- FR-023: EL-005 MUST set status to PAID, paid_at to the current time, and paid_amount to the total paid amount when the PortOne payment status is paid and the total paid amount equals the amount of the Payment record.
- FR-024: EL-005 MUST return the Payment record after applying FR-023.

### Amount mismatch

- FR-068: When EL-005 or EL-032 finds that the PortOne payment status is paid and the total paid amount differs from the amount of the Payment record, the Package MUST send a cancellation request containing the Payment ID and the reason set by EL-037, without an amount.
- FR-069: After PortOne accepts the cancellation request of FR-068, the Package MUST set status to AMOUNT_MISMATCH_CANCELLED, paid_amount to the total paid amount, and cancelled_amount to the total paid amount. It MUST NOT change amount or paid_at.
- FR-070: When the cancellation request of FR-068 fails, the Package MUST set status to AMOUNT_MISMATCH and paid_amount to the total paid amount. It MUST NOT change amount, cancelled_amount, or paid_at.
- FR-071: EL-005 on a Payment record whose status is AMOUNT_MISMATCH_CANCELLED or AMOUNT_MISMATCH MUST NOT send any request to PortOne and MUST throw the exception of ERR-007 built from the stored record.
- FR-072: After FR-069, EL-032 MUST finish without an exception. After FR-070, EL-032 MUST fail with the PortOne exception of the cancellation request, unwrapped.

### Refund

- FR-025: EL-006 MUST send a cancellation request containing the Payment ID and the given reason to PortOne when the Payment record status is PAID or PARTIALLY_CANCELLED.
- FR-026: EL-006 MUST omit the amount from the cancellation request when the given amount is null.
- FR-027: EL-006 MUST include the given amount in the cancellation request when the given amount is not null.
- FR-028: After PortOne accepts the cancellation request, EL-006 MUST increase cancelled_amount by the given amount when the given amount is not null, and MUST set cancelled_amount equal to amount when the given amount is null.
- FR-029: After applying FR-028, EL-006 MUST set status to CANCELLED when cancelled_amount equals amount, and MUST set status to PARTIALLY_CANCELLED otherwise.
- FR-030: EL-006 MUST return the Payment record after applying FR-029.

### Payment history

- FR-031: EL-007 MUST return the Payment records of the Billable model ordered by created_at descending.
- FR-032: EL-008 MUST return the Payment record with the given Payment ID that belongs to the Billable model, or null if none exists.

### Webhook

- FR-033: The Package MUST register a POST route at the path set by EL-018, named portone.webhook.
- FR-034: The route of FR-033 MUST accept requests without authentication and without a CSRF token.
- FR-035: The Package MUST verify each webhook request using the raw request body, EL-012, and the value of EL-016.
- FR-036: The Package MUST dispatch exactly one WebhookReceived event per verified webhook request.
- FR-037: The Package MUST dispatch WebhookReceived for a verified webhook of any type, including a type the Package does not recognize.
- FR-038: The Package MUST respond with HTTP 200 and an empty body after dispatching WebhookReceived.
- FR-039: The Package MUST NOT create, modify, or delete any Customer record or Payment record while handling a webhook request, except the cancellation sync of FR-081.

## User Flows

### FLOW-001 Single payment

- Step 1: Developer calls EL-004 -> Payment record with status PENDING.
- Step 2: Developer calls EL-010 -> array of values for the PortOne browser SDK.
- Step 3: Developer's Application code opens the PortOne payment window; the Payer pays outside the Package.
- Step 4: Developer calls EL-005 -> Payment record with status PAID, or an error defined by ERR-006, ERR-007, ERR-011.
- Step 5: Paid with a different amount -> the payment is cancelled at PortOne -> Payment record with status AMOUNT_MISMATCH_CANCELLED (or AMOUNT_MISMATCH when the cancellation fails) -> AmountMismatchException.

### FLOW-002 Refund

- Step 1: Developer calls EL-006 with a Payment ID and a reason -> Payment record with status CANCELLED.
- Step 2: Developer calls EL-006 with a Payment ID, a reason, and an amount -> Payment record with status PARTIALLY_CANCELLED or CANCELLED.

### FLOW-003 Webhook receipt

- Step 1: PortOne sends a POST request to EL-011 -> signature verified.
- Step 2: Verification succeeds -> WebhookReceived dispatched, HTTP 200.
- Step 3: Verification fails -> HTTP 400, no event.

### FLOW-004 Payment history

- Step 1: Developer calls EL-007 -> Payment records ordered newest first.
- Step 2: Developer calls EL-008 with a Payment ID -> one Payment record or null.

### FLOW-005 Checkout with published stubs

- Step 1: Developer runs vendor:publish with EL-024 and includes EL-030 -> the routes of EL-030 exist.
- Step 2: Payer visits portone.checkout -> EL-025 in the Initial state.
- Step 3: Payer clicks EL-026 -> Loading state; a Payment record with status PENDING exists.
- Step 4: PortOne payment window opens; Payer pays outside the Package.
- Step 5: Payment completes -> complete route -> Payment record with status PAID -> Success state.
- Step 6: Payment does not complete -> Error state; Payment record keeps status PENDING.
- Step 7: After the Success state -> the browser navigates to portone.checkout.completed -> EL-036 shows the paid payment.

### FLOW-006 Expiry of abandoned payments

- Step 1: The Application's scheduler runs EL-031 -> one EL-032 is queued per PENDING record older than EL-033.
- Step 2: EL-032 runs for a record that is still PENDING -> PortOne lookup.
- Step 3: Paid with the same amount -> Payment record with status PAID.
- Step 4: Not paid at the time of the check -> Payment record with status EXPIRED.
- Step 4a: Paid with a different amount -> the payment is cancelled at PortOne -> Payment record with status AMOUNT_MISMATCH_CANCELLED; when the cancellation fails, status AMOUNT_MISMATCH and the job fails.
- Step 5: Anything else -> Payment record unchanged; checked again by a later run of EL-031.
- Step 6: The Application's scheduler runs model:prune -> EXPIRED records older than EL-034 are deleted.
- Step 7: The Developer calls EL-005 for an EXPIRED record that was paid later -> Payment record with status PAID.

## Error Conditions

- ERR-001: EL-015 is unset or empty when EL-005 or EL-006 must send a request to PortOne -> throw ConfigurationException; send no request; change no record.
- ERR-002: EL-016 is unset or empty when a webhook request arrives -> respond HTTP 500; dispatch no event; change no record.
- ERR-003: EL-005 or EL-006 receives a Payment ID with no Payment record belonging to the Billable model -> throw PaymentNotFoundException; send no request.
- ERR-004: EL-004 receives an amount less than or equal to 0 -> throw InvalidArgumentException; create no record.
- ERR-005: EL-004 receives an empty order name -> throw InvalidArgumentException; create no record.
- ERR-006: EL-005 finds the PortOne payment status is not paid -> throw PaymentNotPaidException; leave the Payment record unchanged.
- ERR-007: EL-005 finds the PortOne payment status is paid and the total paid amount differs from the amount of the Payment record -> apply FR-068 through FR-070, then throw AmountMismatchException carrying the total paid amount (paidAmount) and whether PortOne accepted the cancellation (wasCancelled). When the cancellation failed, the exception's previous exception is the PortOne exception.
- ERR-008: EL-006 receives a Payment ID whose Payment record status is PENDING, EXPIRED, CANCELLED, AMOUNT_MISMATCH_CANCELLED, or AMOUNT_MISMATCH -> throw InvalidPaymentStatusException; send no request.
- ERR-009: EL-006 receives an empty reason -> throw InvalidArgumentException; send no request.
- ERR-010: EL-006 receives an amount less than or equal to 0, or greater than amount minus cancelled_amount -> throw InvalidRefundAmountException; send no request.
- ERR-011: A PortOne request other than the cancellation request of FR-068 fails in EL-005 or EL-006 -> throw the PortOne exception without wrapping; leave the Payment record unchanged.
- ERR-012: Webhook verification fails because the signature is invalid, a required header is missing, or the timestamp is outside the allowed range -> respond HTTP 400; dispatch no event; change no record.

- ERR-013: EL-025 is rendered while EL-022 or EL-023 is unset or empty -> EL-025 renders in the Error state with EL-026 disabled.
- ERR-014: EL-005 throws PaymentNotFoundException, PaymentNotPaidException, or AmountMismatchException inside the complete action -> respond HTTP 422 with JSON containing the key error.
- ERR-015: EL-005 throws ConfigurationException or the PortOne exception inside the complete action -> respond HTTP 500 with JSON containing the key error.
- ERR-017: EL-042 receives a Payment ID with no Payment record -> throw PaymentNotFoundException; send no request.
- ERR-018: EL-045 receives a Payment ID with no Payment record -> throw PaymentNotFoundException; send no request. A PortOne request failure in EL-045 throws the PortOne exception unwrapped and leaves the record unchanged; EL-015 unset throws ConfigurationException (ERR-001).
- ERR-019: EL-016 is unset or empty when EL-050 or EL-051 must sign a webhook -> throw ConfigurationException (EL-050) or exit with a failure code (EL-051); send nothing.
- ERR-016: EL-015 is unset or empty, or the PortOne lookup fails for a reason other than those of FR-061, when EL-032 runs -> EL-032 fails with ConfigurationException or the PortOne exception unwrapped; leave the Payment record unchanged. A failed cancellation request of FR-068 is handled by FR-070 and FR-072.

## Non-Goals

- Subscriptions and recurring payments.
- PortOne V1 API.
- Automatic registration of the routes of EL-030.
- Installation of the npm package @portone/browser-sdk.
- Deleting, archiving, or managing statutory retention of Payment records whose status is PAID, PARTIALLY_CANCELLED, or CANCELLED.
- Scheduling, queue configuration, and queue workers of the Application.
- Retrying a failed automatic cancellation. The Developer finds AMOUNT_MISMATCH records and handles them; when the Developer cancels such a payment at PortOne, FR-081 or EL-045 records it.
